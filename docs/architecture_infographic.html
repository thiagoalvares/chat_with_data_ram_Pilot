⚠️ The Golden Rule

The analytical core is byte-for-byte identical to the validated prototype. These files are NEVER modified — they're the proven, tested heart of the application:

• services/llm.py — Two-call LLM pipeline (Call 1: code, Call 2: answer)
• services/executor.py — Executes pandas code in isolated namespace
• services/file_handler.py — CSV/Excel reading, schema extraction
• prompts/standard.py — Standard mode system prompts
• prompts/variance.py — Variance mode system prompts

Everything else is infrastructure — the harness we've built around these core files to make the app production-ready.

What Makes This App Different

🎯 Not Just "Chat with AI"
  • Stateful + In-RAM: ONE Python process, all session data in memory (fast follow-ups)
  • Two-Call Pipeline: LLM generates pandas code → execute → LLM explains result
  • Per-User API Keys: Every user brings their own LiteLLM key (Fernet encrypted)
  • Exact Cost Tracking: Token-level usage logging with model-specific pricing
  • Session-Based Model Selection: Users choose their AI model per session
  • Zero Estimation: Every number comes from executed pandas code, not AI guesses
  • Request Context: Thread-safe per-request state for keys/models (contextvars)
  • Usage Capture Proxy: Intercepts responses to log tokens WITHOUT modifying core files

Design Philosophy

🧱 The Harness Approach
  • Analytical core = untouchable: Proven prototype logic stays frozen
  • Infrastructure = flexible: Add features via wrappers, proxies, envelopes
  • Additive only: New features wrap around core, never modify it
  • Fail-safe: Every safeguard can fail without breaking the core pipeline
  • Thread-safe: Single process, many threads (I/O-bound workload)
  • Session-scoped: In-RAM state clears on restart (acceptable for pilot)

The Two-Call Pipeline

Every question flows through this exact sequence. This is the proven prototype logic that never changes.

1
📤 User Asks Question
Browser sends question + mode to .NET → .NET forwards to Python with X-Session-Id header. Python loads session from RAM, retrieves uploaded DataFrame.
2
🧠 Call 1: Generate Pandas Code
llm.generate_query_code() sends schema + question to LLM (temp=0 for determinism). Returns Python code that queries the DataFrame. No execution yet.
File: services/llm.py + prompts/standard.py
3
⚙️ Execute Code
executor.execute_generated_code() runs the code in an isolated namespace. DataFrame is pre-loaded as df. Returns result + metadata (type, shape). If execution fails → inject error into prompt → retry once.
File: services/executor.py
4
📊 Call 2: Generate Human Answer
llm.generate_human_answer() sends result + metadata to LLM (temp=0.3 for natural language). Returns JSON: {"answer": "...", "chart": {...}} Enhanced JSON parsing strips GPT prefixes, handles markdown fences.
File: services/llm.py + prompts/standard.py
5
🎨 Render Chart (Frontend)
Browser receives answer + chart spec. If chart exists, Chart.js renders it (bar/line/pie/scatter). User can switch chart types client-side (same data, different visualization).
File: dotnet-app/wwwroot/index.html
6
💾 Store + Log
Session updated with last result (for Excel export + refine feature). Usage capture writes token counts + cost to database. History appended (for conversational context in next question).

Auto-Retry Logic

🔄 When Code Execution Fails
  • Capture error message from executor
  • Inject error into prompt: "Your code failed with: [error]. Return ONLY fixed code."
  • Call LLM again (Call 1 retry)
  • Execute retry code
  • If retry fails → return error to user (no infinite loop)
  • If retry succeeds → continue to Call 2 as normal

Prompt Engineering Safeguards

🧮 No Estimation Rule
Critical: All numbers must come DIRECTLY from the data result or metadata. Never calculate, count, sum, estimate, or derive numbers yourself. Even for "insights" — no speculation. If data is truncated (...), write "Data not available" instead of guessing.
prompts/standard.py (line 90-96)
📏 Row Count Clarity
The CSV header row is NOT in the DataFrame — it's been converted to column names. df.shape[0] and len(df) return ONLY data rows. Do NOT add +1 or -1. If CSV has 1 header + 100 data rows, then len(df) = 100 (correct answer).
prompts/standard.py (line 9-11)
📐 Planning Guidance
For complex multi-step operations: plan your approach before coding. Break into 2-3 clear intermediate steps with descriptive variable names (e.g., df_grouped, df_merged). Aim for code under 100 lines. Ensure all string literals, parentheses, and brackets are properly closed.
prompts/standard.py (line 42-44)
🧹 Data Cleaning Rules
Always apply before modeling: convert dates with pd.to_datetime(..., errors='coerce'), convert Categorical columns to string, strip currency symbols, use pd.to_numeric(..., errors='coerce'), drop or fill NaN values before fitting any ML model.
prompts/standard.py (line 25-31)

The Harness: Production Safeguards Around the Core

These are the layers we've built around the analytical core to make it production-ready.

🔐 Per-User API Keys (Encrypted)
Every user stores their OWN LiteLLM key. Keys are Fernet-encrypted before storage in SQLite. On every request: decrypt user's key → set in request_context → config.py serves it to llm.py. Golden rule preserved: llm.py unchanged, just reads from Config.LITELLM_API_KEY.

Blocking onboarding modal when no key is set. Key validation on save. Admin can see usage but cannot see other users' keys.
services/crypto.py, services/database.py, app.py (_resolve_user_context)
🧵 Thread-Safe Per-Request Context
Single Python process, many threads (I/O-bound). How do we serve different users' keys/models per request?

Answer: contextvars. request_context.py uses Python's contextvars module. Each request gets its own isolated context: user_api_key.set(), active_model.set(). Config.py uses @property to read from context dynamically.

Request starts → request_context.begin(key, model) → returns token → request ends → request_context.end(token) cleans up.
services/request_context.py, config.py (dynamic properties)
📊 Usage Capture WITHOUT Modifying Core
The Problem: We need to log tokens/cost from every LLM call, but llm.py is read-only.

The Solution: Proxy pattern. usage_capture.install() swaps llm.requests (the imported requests library) with a thin proxy. The proxy delegates to real requests, but intercepts responses to copy the usage block into request_context.

After pipeline finishes, usage_capture.flush() writes records to database with user/session/question context. llm.py file is byte-identical — it still calls requests.post() exactly as before.
services/usage_capture.py, app.py (flush after ask/refine)
🎛️ Session-Based Model Selection
Users can override the admin default model for their session (in-RAM, lost on restart). Dropdown in header shows 4 verified working models with pricing. Badge shows active model.

Flow: User changes dropdown → /api/user/set_model → saves to session.user_model_preference → next /api/ask → _resolve_user_context() checks session → passes to request_context.begin() → config.py serves it to llm.py.

Falls back to admin default when no preference set. Admin can change global default (all new sessions use it).
services/data_manager.py (user_model_preference), app.py (set_model/get_model)
💰 Exact Cost Tracking
Every LLM call logs: prompt_tokens, completion_tokens, total_tokens, model name. Cost calculated using model-specific pricing: (tokens / 1M) × price_per_1M.

Stored in UsageLog table with: UserID, SessionID, RequestID (one per question), Mode, QuestionText (truncated 500 chars), CallType (call1_codegen, call2_answer, refine_answer), timestamp, success flag.

Dashboard shows: total questions (COUNT DISTINCT RequestID), total cost, avg cost per question, usage over time chart, history table. Admin sees all users aggregated.
services/database.py (UsageLog table), services/pricing.py, app.py (flush)
🧪 Enhanced Multi-Model JSON Parsing
Different models format JSON differently. GPT adds prefixes like "Here's the answer: {...}". Some models wrap in markdown fences: ```json {...} ```.

Solution: parse_answer_response() in llm.py strips known prefixes, removes markdown fences, finds first { and last }, extracts just the JSON.

Plus: For GPT/o1 models, we set response_format: {"type": "json_object"} in the API call (JSON mode) — forces valid JSON at the source. Two-layer defense.
services/llm.py (parse_answer_response, force_json parameter)
🔒 Identity & Authorization
Identity: X-User header from .NET. When Windows Auth is ON = Windows username. When OFF = Auth:DevUsername (appsettings) or machine username. No separate login system.

Admin: ADMIN_USERS env var (comma-separated). is_admin() checks username. Admin endpoints use @require_admin decorator (403 if not admin).

Optional: INTERNAL_API_SECRET — shared secret between .NET and Python. Enable when Python runs on different machine than .NET (prevents X-User spoofing on network).
app.py (_username, _check_internal_secret), services/admin_auth.py
💾 In-RAM Session Storage (Stateful)
All session state lives in Python process memory (STORAGE_BACKEND=memory). Keyed by X-Session-Id from .NET cookie.

What's stored: uploaded DataFrames (standard/variance), schema, chat history (per mode), last result (for Excel export), user model preference, file labels.

Trade-off: Fast (no DB/disk I/O), but restart clears all. Acceptable for pilot. ONE process only — never run multiple workers (would split sessions).
services/data_manager.py (SessionData class), services/storage.py (memory backend)
📝 Conversational History (Mode-Specific)
Chat history stored per mode (standard/variance separate). Last Q&A pair sent to LLM for context. Helps with follow-up questions: "what about the top 10?" → LLM sees previous question + result.

Clear Chat: Clears only the active mode's history (per-tab transcript in frontend). Upload clears its own mode's history (doesn't touch other modes).
services/data_manager.py (history_standard, history_variance), app.py (clear_history)

Infrastructure Components

🗄️ Database (SQLite with WAL)

Tables & Purpose
  • Users: UserID, Username, APIKey (encrypted), CreatedAt, UpdatedAt, LastLogin, IsActive
  • UsageLog: LogID, UserID, Username, SessionID, RequestID, Timestamp, Mode, QuestionText (500 chars), CallType, Model, PromptTokens, CompletionTokens, TotalTokens, PromptCost, CompletionCost, TotalCost, Success, ErrorMessage
  • ModelConfig: ConfigID, ModelName, IsActive (only one active), SetBy, SetAt, InputPrice, OutputPrice
  • ModelChangeLog: ChangeID, PreviousModel, NewModel, ChangedBy, ChangedAt, Reason
  • DataExperts: ExpertID, Label, Description, FilePath, SheetName, AccessMode, AllowedUsers, AllowedGroups, RecommendedQuestions, Rows, Cols, IsActive, CreatedBy, CreatedAt, UpdatedBy, UpdatedAt, SourceType, SourceConfig, SqlQuery
Design Notes
  • WAL journal mode: Safe concurrent readers with writes (single process, many threads)
  • RequestID: One UUID per question. Questions counted as COUNT(DISTINCT RequestID). Survives retries.
  • Timestamps: All stored as UTC 'YYYY-MM-DD HH:MM:SS' strings. Consistent comparisons.
  • DB path: Anchored to python-service folder (not CWD). Override with DB_PATH env.
  • QuestionText truncated: 500 chars (analytics doesn't need full prompts on disk forever)

🔧 Configuration Management

Environment Variables (.env)
  • LITELLM_API_BASE: Gateway URL (e.g., https://aigateway.ga.com)
  • LITELLM_API_KEY: Fallback key (used when user has none, or for admin endpoints)
  • LLM_MODEL: Fallback model (used when no admin default set in DB)
  • LLM_MAX_TOKENS: Default 1024 (code gen), 4096 (answer gen)
  • LLM_TIMEOUT: Default 120 seconds
  • ENCRYPTION_KEY: Fernet key for API key encryption (required for rollout)
  • ADMIN_USERS: Comma-separated usernames (e.g., "alice,bob,charlie")
  • INTERNAL_API_SECRET: Optional shared secret (.NET sends in X-Internal-Auth)
  • DB_PATH: Optional override for chatdata.db location
  • STORAGE_BACKEND: memory (default), disk, sqlserver (memory only for this pilot)
Dynamic Properties (config.py)
  • Config.LITELLM_API_KEY: Reads from request_context.user_api_key or falls back to _ENV_LITELLM_API_KEY
  • Config.LLM_MODEL: Reads from request_context.active_model or falls back to _ENV_LLM_MODEL
  • These properties are called by llm.py — it stays unchanged, config.py handles the routing

🚀 Serving & Deployment

Local Development
  • ./run.sh (macOS/Linux) or .\run.ps1 (Windows): Starts both .NET and Python
  • .NET: dotnet run -c Release (port 5080)
  • Python: python app.py (Flask dev server, port 8000)
  • Open http://localhost:5080
Production (Single Server)
  • Python: python serve.py — Waitress WSGI server, ONE process, WAITRESS_THREADS (default 16), binds 127.0.0.1:8000
  • .NET: IIS hosting, points PythonService:BaseUrl at http://localhost:8000
  • Windows Service: Use NSSM to register serve.py for auto-start/restart
  • Environment: Requires .NET SDK 8.0, Python 3.10+, pip install -r requirements.txt
⚠️ Critical Constraints
  • ONE process only: Never run multiple Python workers/instances (in-RAM sessions would split)
  • Threads are fine: Workload is I/O-bound (waiting on LLM), threads handle concurrency
  • Restart = data loss: All sessions cleared (no persistence by design)
  • Port 5000 on macOS: AirPlay conflict — .NET uses 5080 instead
  • Windows: Use waitress (serve.py), not gunicorn (Linux-only)

Rollout Batch Features (Production-Ready)

These features were added in three rollout batches to make the app enterprise-ready.

🔐 Batch 1: Per-User Keys, Usage Tracking, Admin

What It Adds
  • Per-User API Keys: Every user stores their OWN LiteLLM key (Fernet encrypted in chatdata.db). Blocking onboarding modal if no key set.
  • Usage Tracking: Every LLM call logged: tokens, cost (model-specific pricing), call type, timestamp, success flag. Written to UsageLog table via usage_capture proxy.
  • My Usage Dashboard: Total questions, tokens, cost, avg cost per question. Chart over time (last 30 days). History table (last 20 questions).
  • Admin Dashboard: All users aggregated. Top users by cost. Usage by model. All users list with last login.
  • Global Model Selection: Admin changes default model for all new sessions. Change log tracked (who changed, when, reason).
  • Identity: X-User from .NET (Windows Auth username or dev fallback). ADMIN_USERS env var.
  • Optional Security: INTERNAL_API_SECRET for .NET ↔ Python authentication (when on different machines).
Mechanism (Golden Rule Preserved)
  • Request context: Per-request API key + model set via contextvars (thread-safe)
  • Config.py: Dynamic properties read from request_context, fall back to env vars
  • llm.py: Unchanged — still reads Config.LITELLM_API_KEY and Config.LLM_MODEL
  • Usage capture: Proxy pattern — swaps requests library reference, intercepts responses, extracts tokens

📊 Batch 2: Data Experts (Admin-Published Datasets)

What It Adds
  • Experts: Admins upload datasets (CSV/Excel) → publish with label, description, access control
  • Access Control: Public (all users) OR restricted (specific users OR AD groups)
  • Recommended Questions: Admin writes up to 6 starter questions → become user's chips
  • Loading: Files stored in python-service/datasets/ (gitignored). Loaded via EXACT upload path (disk shim) → pipeline untouched.
  • UI: Left sidebar shows available experts. Click to load → acts like file upload (same flow).
  • Groups: X-User-Groups header from .NET (AD groups from Windows badge). Auth:DevGroups simulates in dev.

⚡ Batch 3: Live Data Sources (Azure + SQL Server)

What It Adds
  • Query-backed experts: Source = Azure blobs (parquet/csv/xlsx) OR SQL Server/Azure SQL
  • Azure blobs: Downloaded with app's Entra service principal (AZURE_TENANT_ID/CLIENT_ID/CLIENT_SECRET). Admin's SQL runs locally in DuckDB (blobs as tables named by aliases).
  • SQL Server: DATABASE runs the SQL. Windows auth = service's own identity (gMSA, no stored password) OR SQL login (Fernet-encrypted).
  • Fetched live: Every time expert is loaded (not cached). Result fed as CSV bytes through SAME _handle_upload shim → pipeline untouched.
  • Guards: DATASOURCE_MAX_ROWS (500k) + the 50 MB working cap. Header shows "⚡ Azure integrated" badge when live expert visible.
  • Admin form: Source picker (file/azure_blob/sql_server), connection config, SQL query, Test query button (executes once before save).
Implementation Notes
  • Lazy imports: services/data_sources.py imports duckdb/azure/pyodbc only when needed. Service runs without them installed (file mode).
  • Not yet tested: Against real Azure account or SQL Server (needs credentials from ITS).
  • ITS asks: Two new egress destinations for batch 3 (Azure Storage, Azure SQL). See ROLLOUT_FEATURES.md.
