System Overview

Chat with Data is an AI-powered data analysis platform that enables users to query uploaded datasets using natural language. The system generates executable pandas code, runs it against the data, and returns human-readable answers with optional visualizations. Every numerical result comes from executed code, not AI estimation.

Key Architectural Principles

⚠️ The Golden Rule: Analytical Core Immutability

The analytical core is byte-for-byte identical to the validated prototype. These files are production-frozen and never modified:

  • services/llm.py — Two-call LLM pipeline (code generation → answer generation)
  • services/executor.py — Secure pandas code execution in isolated namespace
  • services/file_handler.py — CSV/Excel reading and schema extraction
  • prompts/standard.py — System prompts for Standard mode
  • prompts/variance.py — System prompts for Variance mode

All production features are implemented as infrastructure layers around this core. This design ensures the proven analytical logic remains unchanged while adding enterprise capabilities.

Design Philosophy

🧱 Infrastructure as a Harness
All enterprise features are implemented as wrappers, proxies, and envelopes around the analytical core. This "harness" approach allows feature development without touching validated logic. Per-user keys, usage tracking, and model selection all operate via request context and proxies—the core files remain unchanged.
🧵 Thread-Safe Single Process
Runs as ONE Python process with multiple threads (I/O-bound workload). Per-request state (API keys, models) managed via Python's contextvars for thread-safety. Session data stored in-RAM for fast follow-ups. Never run multiple workers—this would split in-RAM sessions across processes.
🎯 Zero Estimation Principle
Every number comes from executed pandas code, not AI guesses. The LLM generates code → code executes → LLM explains the result. Prompt engineering enforces: "All numbers must come DIRECTLY from the data. Never estimate."

Deployment Constraints

Critical: Single Process Architecture

  • ONE Python process only — Multiple workers would split in-RAM session storage
  • Threads for concurrency — Workload is I/O-bound (waiting on LLM), threads handle load
  • Restart clears sessions — No persistence by design (acceptable for pilot scale)
  • Scale up, not out — Increase CPU/RAM on one server, don't add servers
  • For multi-server scale-out — Use the alternate repo with SQL Server + file share backend

State Management

In-RAM Session Storage

All user session data resides in Python process memory (STORAGE_BACKEND=memory). Keyed by X-Session-Id from .NET session cookie.

What's Stored Per Session:

  • Uploaded DataFrames (standard/variance modes)
  • Schema information (column names, types, samples)
  • Chat history (per mode, for conversational context)
  • Last query result (for Excel export + refine feature)
  • User model preference (session-scoped override)
  • File labels and metadata

Trade-off: Fast (no disk/DB I/O) but volatile (restart clears all). For persistent storage, use the SQL Server backend variant.

Request Context (Thread-Safe State)

🧵 Python contextvars for Per-Request State
Single Python process serves multiple users via threads. Each request gets isolated context using Python's contextvars:
  • request_context.user_api_key — User's decrypted LiteLLM key
  • request_context.active_model — User's model preference or admin default
  • request_context.usage_records — Token counts for this request
Config.py uses @property decorators to read from context dynamically. The analytical core (llm.py) calls Config.LITELLM_API_KEY and Config.LLM_MODEL—unchanged—while config.py serves per-request values.

Prompt Engineering Safeguards

🧮 Zero Estimation Rule
Critical instruction in system prompt: "All numbers in your answer must come DIRECTLY from the data result or metadata. Never calculate, count, sum, estimate, or derive any numbers yourself. Even if the user asks for 'insights,' ALL numbers must come from the data—no speculation." This ensures every numerical result is computed by executed pandas code, not AI estimation.
📏 Row Count Clarity
Prevents off-by-one errors: "The CSV header row is NOT in the DataFrame—it's been converted to column names. df.shape[0] and len(df) return ONLY data rows. Do NOT add +1 or -1. If CSV has 1 header + 100 data rows, then len(df) = 100 (correct answer)."
📐 Planning Guidance
For complex queries: "Plan your approach before coding. Break into 2-3 clear intermediate steps with descriptive variable names. Aim for code under 100 lines. Ensure all string literals, parentheses, and brackets are properly closed." Reduces syntax errors in generated code.
🧹 Data Cleaning Rules
Always apply before modeling: Convert dates with pd.to_datetime(..., errors='coerce'). Convert Categorical columns to string. Strip currency symbols. Use pd.to_numeric(..., errors='coerce'). Drop or fill NaN values before ML model fitting.

Complete Request Pipeline

Step-by-step flow from user question to final answer.

1
User Submits Question
Browser sends POST to .NET /ask endpoint with question text and mode (standard/variance). .NET resolves session cookie (cwd_sid), extracts Windows username (if auth enabled).
dotnet-app/Program.cs → ProxyJson()
2
.NET Proxies to Python
.NET forwards request to Python /api/ask with headers:
• X-Session-Id — Session identifier
• X-User — Windows username or dev fallback
• X-Internal-Auth — Optional shared secret (if configured)
dotnet-app/Program.cs
3
Authentication Envelope
_resolve_user_context(username, session):
1. Look up user in database by username
2. Decrypt their API key (Fernet)
3. Check session for user's model preference → fall back to admin default
4. Returns (user, api_key, model_name) or error response

request_context.begin(api_key, model_name) → Sets thread-local context for this request
app.py (_resolve_user_context), services/request_context.py
4
Load Session Data
Retrieve session from in-RAM storage using X-Session-Id:
• Uploaded DataFrame(s)
• Schema information
• Chat history (for conversational context)
• Last result (if exists)
services/data_manager.py (get_session)
5
Call 1: Generate Pandas Code
Build messages: system prompt + schema + question + history (last Q&A pair)
llm.generate_query_code(messages, temp=0)
LLM generates Python code that queries the DataFrame. Deterministic (temp=0).
Code stored in debug log.
services/llm.py, prompts/standard.py
6
Execute Generated Code
executor.execute_generated_code(code, df=df)
Runs code in isolated namespace. DataFrame pre-loaded as df.
Returns: (success, result_str, raw_result, metadata)
Metadata includes: type (DataFrame/Series/scalar/list), rows, columns, column names
services/executor.py
7
Auto-Retry on Execution Failure
If execution fails:
1. Inject error message into prompt: "Your code failed with: [error]. Return ONLY fixed code."
2. Call 1 again (retry)
3. Execute retry code
4. If retry fails → return error to user (no infinite loop)
5. If retry succeeds → continue to Call 2
app.py (_run_pipeline)
8
Call 2: Generate Human Answer
Build messages: system prompt + question + result_str + metadata
llm.generate_human_answer(messages, temp=0.3, force_json=True)
LLM generates JSON: {"answer": "...", "chart": {...}}
More creative (temp=0.3). Force JSON mode for GPT models.
services/llm.py, prompts/standard.py
9
Parse JSON Response
llm.parse_answer_response(raw)
Enhanced parsing: strips GPT prefixes ("Here's the answer:"), removes markdown fences, finds first { and last }, extracts clean JSON.
Returns: (answer_text, chart_spec) or (raw, None) if parsing fails
services/llm.py
10
Update Session + Usage Tracking
Store in session:
• Last result (for Excel export)
• Last question + metadata (for refine feature)
• Append Q&A to history (for next question's context)

Usage tracking (via proxy):
• usage_capture.flush() writes token counts to database
• Calculates cost using model-specific pricing
• Logs: UserID, SessionID, RequestID, tokens, cost, call type, success
services/data_manager.py, services/usage_capture.py, services/database.py
11
Return Response
Python returns JSON to .NET:
{"answer": "...", "chart": {...}, "debug": [...]}

.NET relays to browser. Browser displays answer, renders chart (Chart.js), adds to transcript, enables actions (refine, export, copy).
app.py → dotnet-app/Program.cs → index.html
12
Cleanup Request Context
request_context.end(ctx_tokens) → Clears thread-local context
Next request will set its own isolated context (different user, different key/model).
services/request_context.py

Optional: Refine Feature (One Sentence / More Detail)

Re-Run Call 2 on Stored Result

Enabled on the latest answer only. User clicks "One Sentence" or "More Detail":

  • Retrieves last question, result_str, metadata from session
  • Modifies question: "Re-explain the result in ONE sentence" or "...in MORE detail"
  • Skips Call 1 + execution entirely — numbers cannot change
  • Runs ONLY Call 2 with modified prompt
  • Returns new answer text (chart spec unchanged)
  • Logs as call_type: refine_answer in UsageLog

Endpoint: POST /api/ask/refine with {"style": "brief" | "detail"}

Security & Authentication

Identity Resolution

👤 X-User Header from .NET
Identity supplied by .NET in X-User header:
• When Windows Authentication is ON → Windows username from badge
• When OFF → Auth:DevUsername from appsettings or machine username

No separate login system. The app relies on infrastructure authentication (Windows Auth or dev override).

Per-User API Keys

1
Onboarding: Key Entry
On first visit, user sees blocking modal: "Enter your LiteLLM API key".
Key format validated (starts with "sk-" or similar). User enters key once.
index.html (onboarding modal)
2
Encryption + Storage
POST /api/user/save_key
Backend encrypts key using Fernet (symmetric encryption):
crypto.encrypt_api_key(plain_key) → encrypted bytes
Stores in Users table: INSERT INTO Users (Username, APIKey, CreatedAt)
Key never stored in plain text.
app.py, services/crypto.py, services/database.py
3
Per-Request Decryption
On every /api/ask request:
1. Look up user by username: db.get_user_by_username(username)
2. Decrypt key: crypto.decrypt_api_key(user["APIKey"])
3. Set in request context: request_context.user_api_key.set(decrypted_key)
4. Config.py serves it to llm.py via @property LITELLM_API_KEY
app.py (_resolve_user_context)
4
LLM Gateway Call
llm.py calls requests.post(url, headers={"Authorization": f"Bearer {Config.LITELLM_API_KEY}"})
Config.LITELLM_API_KEY dynamically returns the current request's user key.
Gateway validates key, processes request, returns response + token usage.
services/llm.py, config.py

Admin Authorization

ADMIN_USERS Environment Variable

Comma-separated list of usernames with admin privileges. Example: ADMIN_USERS=alice,bob,charlie

Admin-Only Endpoints:

  • GET /api/admin/check — Check if current user is admin
  • GET /api/admin/users/list — List all users (username, last login, created date)
  • GET /api/admin/usage/summary — Aggregated usage across all users
  • GET /api/admin/usage/by_user — Top users by cost
  • GET /api/admin/usage/by_model — Usage breakdown by AI model
  • GET /api/admin/models/current — Current global default model
  • POST /api/admin/models/select — Change global default model
  • GET /api/admin/models/available — List available models from gateway
  • GET /api/admin/experts/list — List all Data Experts
  • POST /api/admin/experts/create — Create new Data Expert
  • POST /api/admin/experts/update — Update existing Data Expert

Enforcement: @require_admin decorator on endpoints → returns 403 if not admin

Optional: Internal API Secret

X-Internal-Auth Header

Optional shared secret between .NET and Python. Configure when Python runs on a different machine than .NET.

Why It's Needed:

  • Without it: Anyone on the network can hit port 8000 and claim any X-User (spoofable)
  • With it: .NET sends X-Internal-Auth: [secret] on every request. Python validates match.

Configuration:

  • Python: INTERNAL_API_SECRET=some-random-secret in .env
  • .NET: PythonService:InternalSecret=some-random-secret in appsettings.json

Check: app.py @api.before_request _check_internal_secret() → 401 if mismatch

Data Experts Access Control

🔐 Public vs Restricted Access
Admin publishes datasets with access control:

Public: AccessMode = "public" → All users can see/load
Restricted (Users): AccessMode = "restricted", AllowedUsers = "alice,bob" → Only listed users
Restricted (Groups): AccessMode = "restricted", AllowedGroups = "Finance,HR" → Users in these AD groups

Enforcement: Python checks on /api/experts/list and /api/experts/load
Groups resolved by .NET from Windows badge, sent in X-User-Groups header (comma-separated)

Live Data Sources (Azure + SQL Server)

Query-Backed Experts Security

Data Experts can be backed by live data sources instead of static files:

Azure Blob Storage:

  • App's Entra service principal (AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET)
  • Downloads parquet/csv/xlsx on demand
  • Admin's SQL runs locally in DuckDB (blobs as tables)
  • Guard: DATASOURCE_MAX_ROWS (default 500k)

SQL Server / Azure SQL:

  • Windows Auth: Service's own identity (gMSA, no stored password) — recommended for on-prem
  • SQL Login: Username + password (Fernet encrypted) — for Azure SQL
  • Database runs the SQL query (not DuckDB)
  • Guard: DATASOURCE_MAX_ROWS + 50 MB working cap

Lazy imports: duckdb, azure-storage-blob, pyodbc only imported when needed. Service runs without them (file mode).

Sizing & Capacity

Single-Server Capacity Planning

Workload is I/O-bound (each query waits on LLM). Threads handle concurrency efficiently.

Resource Drivers:

  • RAM: Primary constraint. Each active user's data sits in memory. With files up to ~50 MB, budget a few hundred MB per concurrent active user + OS overhead.
  • CPU: Light (4 vCPUs sufficient for small-to-medium load). Pandas operations + JSON parsing.
  • Network: Outbound to LiteLLM gateway. Typical request: 10-50 KB prompt, 1-5 KB response.

Recommended Specs (Pilot Scale):

  • Small (10-20 users): 4 vCPUs, 16 GB RAM
  • Medium (20-50 users): 8 vCPUs, 32 GB RAM
  • Large (50+ users): Scale up (bigger server) or switch to SQL Server backend variant

Threading: WAITRESS_THREADS=16 (default). Increase if seeing queue delays (check logs). Don't exceed 2× CPU core count.

Deployment Constraints

Critical Constraints for Production

  • ONE Python process only: Never run multiple workers (gunicorn --workers > 1) or multiple instances. In-RAM sessions would split. Use threads for concurrency.
  • Restart clears data: All sessions, uploaded DataFrames, chat history cleared on restart. Users must re-upload. Acceptable for pilot scale.
  • No load balancing: Can't put multiple instances behind a load balancer (session affinity wouldn't help—data lives in process memory).
  • Scale up, not out: To handle more load, increase RAM/CPU on the same server. Don't add servers.
  • For multi-server scale-out: Use the alternate repository variant with SQL Server backend + file share storage. Different architecture.

Monitoring & Maintenance

Log Files

  • Python: python-service/logs/app.log — All requests, LLM calls, errors, timing
  • .NET: Windows Event Viewer (Application log) — IIS errors, startup/shutdown
  • Rotate logs: app.log rotates automatically (10 MB max, 5 backups)

Database Maintenance

  • Backup: Copy chatdata.db regularly (contains usage history, keys, experts)
  • Size growth: UsageLog grows with usage. Expect ~1 KB per question. 1 million questions ≈ 1 GB.
  • Cleanup old data: Manually delete old UsageLog entries if needed (no built-in retention policy)
  • WAL checkpoint: Automatic. SQLite merges WAL file into main DB periodically.

Health Checks

  • Python API: GET /api/health — Returns {"status": "ok"} if running
  • Database: GET /api/admin/users/list (admin only) — Verifies DB connectivity
  • LiteLLM Gateway: GET /api/admin/models/available (admin only) — Verifies gateway connectivity

Disaster Recovery

💾 What to Backup
Critical: python-service/chatdata.db (encrypted keys, usage history, experts)
Critical: python-service/.env (especially ENCRYPTION_KEY — can't decrypt keys without it)
Important: python-service/datasets/ (if using Data Experts with file storage)
Optional: python-service/static/images/ga_logo.png (for Word report branding)

In-RAM data: Cannot be backed up (user sessions, uploaded data). Users re-upload after restart.
🔄 Recovery Procedure
1. Restore .env (especially ENCRYPTION_KEY)
2. Restore chatdata.db
3. Restore datasets/ folder (if applicable)
4. Restart Python service (python serve.py or Windows service)
5. Restart IIS (.NET frontend)

Result: Users can log in (keys decrypted), usage history intact, Data Experts available. In-RAM sessions start fresh.
