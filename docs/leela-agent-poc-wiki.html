System architecture

The agent is ~200 lines of Python wrapped around LiteLLM calls the app already makes. The .NET layer wears a second hat as the DAX bridge (the Power BI client library is .NET-only). All thinking happens in the Python service; everything else is pipes.

Already shipped (Aug 2026): the Agentic AI ✨ mode tab is live in Chat with Data next to Standard and Variance — full-screen greeting, input area, and a "Coming Soon – In Development" badge (commits b35bfcb, ebc8bf1). The input is intentionally disabled; this plan builds the backend it will post to, then flips it on.

Runtime flow — one question end to end

  1. Browser → .NET → Python. The shipped Agentic AI tab posts the question to /leela/ask; the .NET proxy forwards it, same pattern as every existing route.
  2. Python → LiteLLM. The loop sends the conversation plus the tool menu (JSON descriptions of the four functions). The LLM replies with a tool call — never with code that runs anywhere.
  3. Python runs the tool. query_dax calls back to the .NET bridge over localhost; search_docs hits the local FTS5 index; run_pandas uses the untouched golden executor.
  4. Result appended, loop repeats. The LLM sees the result and decides the next step — a different model, a follow-up query, a document lookup — until it has enough.
  5. Final answer + trace. The answer returns with the full step-by-step trace, rendered as a collapsible "How I got this" — the audit trail is the feature.

The golden rule survives intact. The LLM orchestrates and narrates; deterministic code computes. Every figure in an answer traces to a DAX result, a pandas execution, or a quoted document — never the model's memory.

Design decisions locked in

Model strategy

Rent the brain, own the context

No custom or fine-tuned model. Knowledge lives in systems; the agent fetches it live with citations. Registries, tools, and permissions are the moat.

Tool tiers

Verdict vs. exploration

Verdict tools are pre-built and deterministic (DAX measures, thresholds, checks) — the LLM never writes their logic. Exploration (run_pandas) is freeform but read-only and never produces an official verdict.

Document search

Keyword-first, no embeddings

The corpus is acronym-heavy (CDRL, EVMS, WBS) and users complain semantic search misses exact terms. FTS5 exact matching + the agent reformulating queries covers the synonym gap. Embeddings can be added later behind the same tools if miss logs justify it.

Scale path

One agent now, specialists later

This is Option B (one loop, many tools). When the tool menu outgrows one context or other teams ship their own agents, it splits into an orchestrator + specialist agents — same loop, nested. Nothing built here is thrown away.

The .NET bridge

// dotnet-app: dotnet add package Microsoft.AnalysisServices.AdomdClient.NetCore.retail.amd64
app.MapPost("/internal/dax", (DaxRequest req) => {
    var q = req.Dax.TrimStart();
    // Guardrail: read-only — reject anything that is not EVALUATE/DEFINE
    if (!q.StartsWith("EVALUATE", OrdinalIgnoreCase) && !q.StartsWith("DEFINE", OrdinalIgnoreCase))
        return Results.BadRequest(new { error = "Only EVALUATE/DEFINE allowed." });

    using var conn = new AdomdConnection($"Data Source={req.WorkspaceUrl};Initial Catalog={req.Database};");
    conn.Open();  // pops the same Entra sign-in DAX Studio shows — no IT needed
    using var cmd = conn.CreateCommand(); cmd.CommandText = req.Dax;
    using var reader = cmd.ExecuteReader();
    // read rows, cap at 500, return { columns, rows, truncated }
});
  • Auth: interactive Entra sign-in, token cached and silently refreshed. Unattended operation later needs a service principal — the one future IT ask.
  • Security: bind /internal/dax to localhost or protect with the existing INTERNAL_API_SECRET header. Never browser-reachable.
  • Later nicety: pool connections per workspace (ConcurrentDictionary keyed by URL) — first query pays ~2s setup, repeats are instant.

Connection 2 — SharePoint documents (existing Azure sync)

The RAG application's Azure pipelines already sync several SharePoint repositories to Blob Storage nightly. Leela reads those containers directly — reusing the sync investment with zero dependency on the Mendix tool or team.

PieceWhat happens
SyncAlready running — existing Azure jobs land SharePoint files in Blob containers nightly. Nothing to build.
AccessRead-only RBAC on the containers (Storage Blob Data Reader) — a small, one-time ask.
Ingest job~100 lines, nightly after the sync: list blobs → new/changed only → extract text (pypdf, python-docx) → chunk by heading/page (large chunks; FTS needs no micro-chunks) → index.
IndexSQLite FTS5: one row per chunk with filename, section, modified date, and the original SharePoint URL for citations.
Repo registrySame pattern as models: allowlisted containers with a description each, so the agent knows which repo covers what.

Why keyword search wins here

  • Embeddings handle acronyms poorly — CDRL is a rare token with weak vector meaning; semantic search returns "related" docs when users wanted that exact term. This is the documented complaint about the current RAG tool.
  • FTS5 gives grep behavior: exact match first, prefix queries (WBS*), title/heading boosting.
  • An acronym glossary in the system prompt lets the agent search both CDRL and its expansion.
  • The agent retries with reformulated queries — the LLM is the synonym engine, closing most of the gap embeddings would.
  • Log every search miss: that log is the future evidence for (or against) adding embeddings behind the same tools.

Expert config

Experts become agent context

A data expert = a system-prompt fragment (terminology, thresholds, WBS knowledge) plus a tool list. The finance expert and the scheduling expert can expose different model registries.

The loop

An agent is a while-loop in your code plus an LLM that picks the next step. The LLM only ever returns JSON — a tool name and arguments. Your Python executes everything.

# python-service/services/agent_loop.py
MAX_STEPS = 12

def run_agent(question, model):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user",   "content": question}]
    trace = []
    for step in range(MAX_STEPS):
        resp = client.chat.completions.create(model=model, messages=messages, tools=TOOL_DEFS)
        msg = resp.choices[0].message
        if not msg.tool_calls:
            return {"answer": msg.content, "trace": trace}   # final answer
        messages.append(msg)
        for tc in msg.tool_calls:
            name, args = tc.function.name, json.loads(tc.function.arguments)
            try:
                result = TOOL_IMPL[name](args)
            except Exception as e:
                result = json.dumps({"error": str(e)})       # errors fed back — she self-corrects
            trace.append({"step": step, "tool": name, "args": args})
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
    return {"answer": "Step limit reached — try a narrower question.", "trace": trace}

System prompt — the rules that make her trustworthy

You are Leela, a data analyst.
1. Route first: list_models / registry descriptions pick the ONE source that fits.
2. Schema before DAX — never guess table, column, or measure names.
3. Prefer existing measures over hand-rolled math: measures are the company's
   governed definitions and must match the dashboards.
4. Every number in your answer must come from a query result in this conversation.
   Never estimate or fill in numbers yourself.
5. Cite documents by their SharePoint link. Quote exact wording for rules.
6. On errors: read, fix, retry. On repeated misses: reformulate the search.
7. Final answers state which sources were used.

Guardrails (all in the PoC)

Read-only everywhere

DAX bridge rejects non-EVALUATE. Blob access is reader RBAC. Executor writes nothing.

Caps

12 steps per question · 500 rows per DAX result · request timeouts. No runaways.

Full trace

Every step logged (tool, args, duration, tokens) into the existing usage-tracking DB, and shown to the user.

Allowlists

Models and doc repos come only from registries. Access beyond them doesn't exist as far as the agent knows.

Errors recycled

Tool failures return as data, not crashes — the LLM reads the error and self-corrects.

Gateway fallback

If the gateway strips the tools param: same loop, prompted JSON protocol instead. One curl test decides.

Verify first: one curl to the gateway with a tools payload. A tool_calls block in the response = native path. Plain text = use the JSON-protocol fallback — everything else in this plan is identical either way.
