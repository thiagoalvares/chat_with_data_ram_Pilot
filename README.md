# Chat with Data — RAM Pilot (v2 features on the In-RAM Edition)

A **single-server, in-memory** build of Chat with Data: a **.NET (ASP.NET Core)
presentation layer** wrapping a **Python micro-service** that holds all session
state — uploaded data, schema, conversation history, last result — **in server
RAM** for the fastest possible follow-up responses. Scope: the **Standard** and
**Variance** analysis modes.

This is the **pilot build**: a copy of `chat-with-data-RAM` (Option 1 — single
server, everything in RAM) plus the v2 user-experience features below. The
analytical core (two-call pipeline, executor, prompts) remains byte-for-byte
identical to the validated prototype.

## v2 features (all additive; no LLM cost except where noted)

- **Word report export** — one click exports the conversation (questions,
  answers, charts as images, optional Query & Calculations appendix) to a
  GA-branded .docx. Replaces the need for saved history; nothing persists
  server-side. Clear Chat offers the export first.
- **Pin dashboard** — pin any answer; a Dashboard view shows pinned snapshots
  side by side (session-scoped; include them via Export Report).
- **Tab-switch fix** — each tab keeps its conversation on screen until the user
  clears it; uploads clear only their own tab's history.
- **Starter question chips**, **data profile card**, and **anomaly nudges** —
  generated by pure pandas at upload time (services/insights.py). Zero LLM calls.
- **One sentence / More detail** — re-explains the same computed result
  (Call 2 only; the numbers cannot change).
- **Chart type switcher** (bar/line/pie, client-side), **copy answer**,
  **question history dropdown**, **dark mode**, **Variance Baseline/Current
  labels** with dates auto-detected from filenames.

```
 Browser ──► .NET front end (ASP.NET Core)  ──HTTP + X-Session-Id──►  Python (Flask, ONE process)  ──►  LiteLLM gateway
             UI · session cookie · proxy                              two-call pipeline + ALL state in RAM
```

## Why in-RAM (stateful)

Each user's DataFrame(s), schema, conversation, and last result live in the
Python process's memory, keyed by session id. A follow-up question ("now only the
active ones") reuses the data already in RAM — **no reload from disk or a
database** — so responses are fast. The service runs as **one process** so that
memory is shared across all requests.

**Trade-offs (acceptable for a small base):**
- **One server, no redundancy.** If it goes down, it's down until restarted.
- **A restart clears active sessions** — users re-upload. (No data is persisted.)
- Scales *up* (a bigger box), not *out*. To scale out later, switch to the
  `chat-with-data-dotnet` edition (SQL Server + file share + load balancer).

## What you need
- **.NET SDK 8.0** and **Python 3.10+** on one server.
- For **live answers**: the **GA network/VPN** (gateway `aigateway.ga.com`).
- Enough **RAM** for concurrent users' data in memory (see the architecture doc's
  sizing section).

## Run locally
1. `cp python-service/.env.example python-service/.env` and set `LITELLM_API_KEY`
   / `LITELLM_API_BASE`.
2. Start scripts: `./run.sh` (macOS/Linux) or `.\run.ps1` (Windows). Open
   **http://localhost:5080**.
   - Or Docker: `docker compose up --build` (single container, memory backend).
3. **Offline (no VPN):** run `python python-service/mock_llm.py` (:9000) and point
   the service at it with `LITELLM_API_BASE=http://localhost:9000` `LITELLM_API_KEY=mock`.

## Run on the server (production, single box)

Run the Python service as **one process** with a thread pool via **waitress**
(works on Windows and Linux; gunicorn is Linux-only):

```bash
cd python-service
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python serve.py            # waitress on 127.0.0.1:8000, one process, 16 threads
```
Then publish the .NET app to IIS (or run `dotnet run`) with
`PythonService:BaseUrl = http://localhost:8000`. On Windows, register
`serve.py` as a Windows service (e.g. via NSSM) so it starts on boot and
restarts on failure. See `docs/` for the full server setup.

> ⚠️ **Do not run multiple Python workers/processes** with this edition — separate
> processes have separate memory and would split user sessions. Concurrency comes
> from threads within the one process (the workload is I/O-bound on the LLM).

## Layout
```
dotnet-app/          ASP.NET Core presentation layer (unchanged from the base repo)
python-service/
  app.py               REST API (upload/ask/export/clear/health)
  serve.py             production entry — waitress, ONE process (in-RAM)   [RAM edition]
  services/llm.py, executor.py, file_handler.py   analytical core (UNCHANGED)
  services/data_manager.py   session state (memory backend)
  storage.py           memory (used) | disk | sqlserver (present but unused here)
  prompts/standard.py, variance.py                (UNCHANGED)
  mock_llm.py          offline test gateway (test only)
  Dockerfile           gunicorn --workers 1 (single process)               [RAM edition]
docker-compose.yml     single container, STORAGE_BACKEND=memory            [RAM edition]
run.sh / run.ps1       local launchers
docs/                  architecture document + diagrams
```
